## Verdict

**Request changes: 2 blocking findings, 4 non-blocking findings, 1 runtime
question.** P1's repository seam is broadly sufficient for P6/P7: it has stable
keyset fields, typed `Result` errors, an absent/pending summary path, a queued
enrichment path, and a first-class digest `preparing` state. P8's palette and
provider design are coherent, but native persistence is non-functional because
the installed SDK-54 module is consumed through the wrong export, and the root
does not actually keep the native splash visible while preference storage loads.

## Blocking findings

### B1 — Native KV calls the module namespace, not the exported store instance

**Measured.** `src/storage/kv.ts:88-96` assigns
`require('expo-sqlite/kv-store')` directly to a fabricated object type and calls
`Store.getItem`. In the exactly pinned installed dependency, the instance is
exported as `default` and `Storage` (`node_modules/expo-sqlite/kv-store.d.ts:2`,
`node_modules/expo-sqlite/build/Storage.d.ts:141-145`); the module namespace does
not itself expose `getItem`/`setItem`/`removeItem`.

Impact: on native, each method lookup is undefined. The wrapper catches the
resulting `TypeError`, warns, and returns `null`/drops the write
(`src/storage/kv.ts:94-116`). Theme selection therefore never survives a native
restart. Because P6/P9 are directed to reuse this adapter, device identity,
user-state, query-cache, onboarding, and notification persistence would inherit
the same failure. The fake-store tests cannot see this because they never invoke
the real module shape.

Smallest safe correction: obtain and validate the actual export, e.g. the
equivalent of `const module = require(...); const Store = module.default ??
module.Storage`, then fail over if the required methods are absent. Add a test
whose mock has the real `{default, Storage}` export shape and a native device or
simulator restart check.

### B2 — Theme readiness paints a dark React frame; it does not hold the splash

**Measured static defect; visual duration needs measurement.** The font gate
returns a dark `View` before `ThemeProvider` is mounted (`app/_layout.tsx:37-45`).
After fonts load, the provider begins its asynchronous read and `ThemedApp`
returns another dark `View` while `isReady` is false (`app/_layout.tsx:62-64`).
There is no `SplashScreen.preventAutoHideAsync()` or matching hide call in the
committed layout.

Impact (inferred): a user whose saved preference is light can see the dark native
splash/background followed by at least one dark React frame before the light UI.
That violates P8's explicit “preference loaded before the first painted frame / keep
the splash up” acceptance contract. Theme loading also starts only after font
loading, lengthening this interval.

Smallest safe correction: prevent automatic splash hide at module startup, mount
the theme provider while fonts load, and hide the splash only after both fonts
and stored preference are ready. Verify launch/restart with a persisted light
preference on iOS and Android.

## Non-blocking findings

### N1 — `Source.feedUrl`'s declared contract disagrees with the mapper and report

**Measured.** The DTO declares `feedUrl: string` (`src/domain/types.ts:28`), while
the mapper deliberately supplies `null` for Anthropic
(`src/data-access/mock/mapper.ts:108-112`), and `p1.md` documents the field as
nullable. `FEED_URLS` is typed `Record<string,string>`, so TypeScript incorrectly
assumes every lookup succeeds and does not expose the mismatch.

Current repository impact is limited because `listSources()` filters inactive
Anthropic out before returning (`src/data-access/mock/repositories.ts:103-105`).
The exported mapper is nevertheless unsound and gives P6 two competing
contracts. Make the map `Partial<Record<string,string>>` and the DTO field
`string | null` as documented, or make `toSourceDto` refuse records without a
feed and retain a non-null DTO.

### N2 — The supposedly opaque cursor is structurally forgeable

**Measured.** `Cursor`'s unique-symbol brand is optional
(`src/domain/types.ts:102-112`), so any `{publishedAt, id}` object satisfies it.
This contradicts the adjacent claim that only the layer or `decodeCursor` can
produce a cursor; no `decodeCursor` exists in P1.

Mock pagination itself is deterministic and correctly applies the descending
tuple comparison (`src/data-access/mock/mapper.ts:150-165`), so this is contract
debt rather than a current pagination failure. Either make the brand required
and expose adapter-owned cursor factories/serialization, or explicitly define
the cursor as a validated serializable value and remove the opacity claim.

### N3 — Web storage errors warn but never switch to the promised memory fallback

**Measured.** When `localStorage` exists but an operation throws, reads return
`null` and writes/removes are discarded (`src/storage/kv.ts:57-78`). The memory
store is selected only when `localStorage` is absent, not when it is blocked or
unusable.

Impact: restricted/private browser contexts lose state even for the current
session, and later P6 consumers will behave as if persistence succeeded. Switch
the adapter to `memoryStore` after the first operation failure (with the existing
one-time warning), and test a throwing `localStorage` implementation.

### N4 — The derived light danger colour narrowly misses AA on the page ground

**Measured.** WCAG relative-luminance calculations give `#DC2626` contrast of
4.829:1 on the white card but 4.466:1 on `#F4F6FB`; the latter is just below the
4.5:1 threshold for normal text. The slot has no committed consumer yet, so no
current screen fails because of it. `toastText #FFFFFF` on `toastBg #0F1B33`
measures 17.144:1, and accent `#2563EB` measures 5.169:1 on white and 4.780:1 on
the page ground.

Use danger only for large/non-text marks on `appBg`, or darken it slightly before
P7/P9 introduce normal-sized danger copy there. The `.35` light scrim is not a
text contrast role; its modal separation remains **needs measurement** at
390×844 on a device.

## Question / needs measurement

### Q1 — Automatic system style with a fixed dark splash/status background

`app.json:9` changes `userInterfaceStyle` to `automatic`, while
`app.json:10,17,30` keep the native/background/splash surfaces dark as required.
Before the JS `StatusBar` mounts (`app/_layout.tsx:68`), a system-light device may
choose dark status-bar content over that dark surface. This is **inferred**;
observe cold launch on system-light iOS and Android to determine whether icons
are unreadable or flash. B2's splash lifecycle correction provides the right
place to set a deterministic pre-ready status style.

their migration to P7 and requires the dark shim in the interim.
