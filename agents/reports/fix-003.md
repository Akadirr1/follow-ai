# fix-003 — Accept content-less feed items; decline enrichment without a body

Implementer report, server lane. **Nothing was deployed and no network was
reached.** The fix is verified against fixtures only; whether Hugging Face
actually ingests after redeploy is the coordinator's re-run.

## The defect

`_shared/feed.ts` dropped any item whose body stripped to an empty string.
Hugging Face publishes `<title>`, `<link>`, `<guid>`, `<pubDate>` and nothing
else — all 845 items — so a **seeded default source ingested 0 articles** while
reporting success. The catalogue promised a source that could never show
anything, and the run counted 845 items as `skipped.no_content`, which reads
like a parser bug rather than a normal feed shape.

The judgement was wrong: a headline and a link are a usable entry. The card
renders, the link works, and only the AI summary is impossible.

### 1. Keep the item (`feed.ts`)

Both `mapRssItem` and `mapAtomEntry` no longer return `null` when the body is
empty. Title, link and date remain load-bearing; the body does not. The item is
emitted with `contentText: ''`, `excerpt: ''`, `quality: 'excerpt'`.

One correctness fix that came with it: `quality` was `encoded !== '' ? 'full' :
'excerpt'`. A `<content:encoded>` that strips to nothing would have claimed
`full` with an empty body — which P2's `articles_full_requires_text` CHECK
rejects outright. It is now `encoded !== '' && contentText !== ''`, same for
Atom.

### 2. How the counter was split

You asked me to say how I split `no_content`. **I dropped it from `SkipReason`
entirely** and added `ParsedFeed.contentless`.

The reason is arithmetic, not taste: `ingest.ts` does
`Object.values(feed.skipped).reduce(...)` to produce the run's `skippedItems`.
Leaving a *kept* item in that record would have made every Hugging Face run
report 845 skipped and 845 inserted from 845 items. `skipped` now means exactly
"dropped"; `contentless` means "kept, no body".

The two cases the old counter conflated are both kept, and both counted the
same way — a fixture covers each:

- **absent** — no `<description>`/`<content:encoded>` element (Hugging Face);
- **stripped to nothing** — the element exists but is an image or a comment.

I did not keep them apart. They are indistinguishable downstream: both produce
`content_text = NULL`, both make enrichment impossible, and neither is a defect
in the item. A second counter would have been a number nobody could act on.

### 3. Absent, not empty (`ingest.ts` + the row type)

`content_text` and `excerpt` are `null` when empty, so the column says "this
feed publishes headlines" rather than "the body was blank".

**`content_hash` is still computed**, over `(title, '')`. Two headlines hash
differently, so a corrected headline still invalidates a cached summary exactly
as a rewritten body would — asserted in a test.

Worth recording: the brief's stated reason for `null` — that
`articles_full_requires_text` and the length checks would trip — **is not a live
risk.** I checked P2's constraints: `articles_full_requires_text` only bites at
`content_quality = 'full'` (these rows are `excerpt`), and both length checks are
`x is null or char_length(x) <= N`, which `''` satisfies. `null` is still the
right choice, for the semantic reason above, not the stated one. I raised this
before implementing and you confirmed.

### 4. The new response shape

```jsonc
// 200 OK — terminal and cacheable
{ "status": "unavailable", "reason": "no_content", "client_request_id": "…" }
```

Not an error: nothing went wrong. The article has no body, no amount of retrying
produces one, and the client shows "Bu haber için özet üretilemiyor" with a link
to the source instead of polling forever.

Placement inside `requestEnrichment` is deliberate:

- **after the cache lookup** — an article enriched while it still had a body
  keeps serving that summary rather than losing it;
- **before the miss budget** — the answer costs no Claude call, so it must not
  consume one of the 30 daily misses. Browsing a headlines-only source would
  otherwise exhaust a user's enrichment quota on articles that were never
  enrichable. Both are asserted.

The check is one predicate, `hasEnrichableBody`, because
`internal_find_article_for_enrichment` and `internal_lease_enrichment_jobs`
already return `coalesce(nullif(content_text, ''), excerpt, '')` — an empty
string there means "no body **and** no excerpt", so one test covers both columns
and reads the same whether the row stores `NULL` or `''`.

### 5. The worker refuses defensively

`runOneJob` fails a bodyless job with code `no_content` **before** touching the
client — no Claude call, no spend on an empty prompt — and fails it *terminally*
rather than retrying, because the body is not coming back. A lost lease is still
reported as `lease_lost`, not as a failure.

**`process-enrichments/index.ts` is unchanged.** The guard belongs in
`runOneJob`, which that function calls; putting it in the handler would have
duplicated the rule and left the pure path untested.

## Tests

512 in the `sql` project, up 16.

- **feed** — the Hugging Face shape keeps every item with empty content, excerpt
  quality, `contentless === items.length`, and **zero skipped**; a body that
  strips to nothing is kept too; a bodyless Atom entry is kept; a feed whose
  items all have bodies reports `contentless: 0`.
- **ingest** — bodyless rows carry `content_text: null` and `excerpt: null`,
  stay `excerpt` quality, and still carry a valid `content_hash` equal to
  `contentHashHex(title, '')`, with two headlines hashing differently;
  `contentlessItems` is reported from a run.
- **enrichment** — `unavailable/no_content` without enqueueing; the miss budget
  is not charged (asserted on the actual `bumpRateLimit` action list);
  whitespace-only content counts as none; a cached summary still wins; the
  worker refuses without calling the client, terminally, and reports
  `lease_lost` correctly.

### One existing assertion changed, deliberately

`feed.test.ts`'s "drops only the broken items" expected
`items === ['Good one']` and `no_content: 1`. The bodyless item is now kept, so
it expects `['No content', 'Good one']` and `contentless: 1`. That test was
asserting the bug.

### One fixture was wrong

`fixtures/feeds.ts` credited Hugging Face with a `<description>`, copied from
the original facts table. The live feed has none — which is precisely why the
fixtures passed while production ingested nothing. **A hand-written fixture that
disagrees with the feed it claims to model is worse than no fixture**, so I
corrected it to the measured shape, gave it a second item so "all items are
contentless" is a real count, and recorded the correction in the provenance
header.

## What is NOT verified

1. **That Hugging Face now ingests.** The fixture matches the shape you
   measured, not the bytes. **Your re-run of `sync-feeds` against the HF source
   is the only real proof** — expect `inserted: 845, contentless: 845` in the
   log line, which is what the new field is for.
2. **That `NULL` bodies insert cleanly.** `internal_upsert_articles` does
   `v_item ->> 'content_text'`, which yields SQL `NULL` for a JSON null. Never
   executed here; no database was reachable.
3. **The `unavailable` response end to end** — the handler branch is unit-tested
   through `requestEnrichment`, but `request-enrichment/index.ts` itself needs
   Deno.
4. **How the client renders `status: 'unavailable'`.** This is a **new response
   variant** the client lane has not seen. Until they handle it, an unknown
   status may fall through to whatever their default branch does. **Route this
   to P7/ver-003.**
5. **The worker's defensive refusal against a real queued job.** No such job
   exists yet, and with no Anthropic key none will run.

## Rollback

Pure code; nothing to un-apply in the database and no migration involved.
`git checkout -- supabase/functions supabase/tests` restores the previous
behaviour, then redeploy `sync-feeds` and `request-enrichment`.

Two things to know before doing that:

- **Rows already ingested stay.** Articles inserted with `content_text = NULL`
  remain valid — the columns are nullable and every CHECK passes. Reverting
  stops new bodyless items arriving; it does not invalidate old ones.
- **Reverting re-breaks Hugging Face.** It ingests nothing again, silently, and
  the run reports the items as skipped. If the goal is only to undo the
  `unavailable` response while keeping ingestion, revert
  `_shared/enrichment.ts` and `request-enrichment/index.ts` alone — the two
  halves are independent.
