## 2. State machine

`canSchedule = granted | provisional`. The three axes and what each cell does:

| permission | `digestEnabled` | OS schedules | what happens |
|---|---|---|---|
| undetermined | false | 0 | idle; the switch is the only thing that asks |
| undetermined | true | 0 | **reconcile** requests permission via `enableDigest`; if refused, flag → false |
| granted / provisional | true | 0 | **reconcile** schedules one (post-reboot, post-DST) |
| granted / provisional | true | 1 | steady state; reconcile confirms the stored id |
| granted / provisional | true | ≥2 | **deduplicate** to the id we know, cancel the rest, warn |
| granted / provisional | false | ≥1 | cancel every owned schedule, clear the id |
| denied | true | ≥1 | revoked in OS settings → cancel, clear id, `digestEnabled=false`, show OS guidance |
| denied | false | 0 | terminal until the user grants it in OS settings; **the time is kept** |
| web / unsupported | any | — | no-op with one warning; the switch reports `unsupported` |

Ordering rules, both tested:

- **Enable / change time**: `ensureChannel` → permission → **schedule new** →
  **persist id** → **cancel old**. A failed schedule returns `schedule_failed`
  and leaves the previous reminder alive, so a bad time change degrades to "the
  time did not change" rather than "notifications silently stopped".
- **Reconcile** runs on mount, on every `AppState` return to `active`, and when
  the UTC offset changes (polled every 60 s — that is the only way a DST shift is
  noticed at all). It only ever touches schedules whose `data.owner` is
  `aigundem.daily-digest`; anything else in the OS queue is left alone.

**Trigger type:** an inexact `{ type: 'daily', hour, minute }` trigger, so
`SCHEDULE_EXACT_ALARM` is **not** requested. A digest that arrives a few minutes
late is fine, and an exact alarm would need an Android 12+ permission and a
store-review justification for no user-visible gain. Stated because the brief
asked for the choice to be explicit.

**Android channel** `daily-digest` is created before every permission request
(Android 13 will not show the dialog for a channel that does not exist);
`ensureChannel` is a no-op on iOS, asserted by a test.

## 3. Onboarding

One scroll, three steps: sources (all on, toggle to narrow), the five digest
slots, and an optional permission ask. "Başla" persists and enters the tabs.

**Completion is ordered, not transactional** — a kv store has no transaction, so
`completeOnboarding` writes sources → settings → **completion marker last**. A
crash part-way leaves no marker, so onboarding replays and overwrites the partial
state; the failure mode is repeating a 20-second flow, never entering the app with
no sources. A test records the write order and asserts the marker is last.

**The guard is structural.** `app/_layout.tsx` uses `Stack.Protected`: an
incomplete device has no `(tabs)` route to navigate to, so Back and a cold restart
cannot step around it — as opposed to a redirect, which can be raced. The
onboarding read joined `isAppReady`, so the splash stays up until it settles and
the first painted frame is already the right screen (fix-002's gate extended, not
regressed).

`digestEnabled` is set from what the OS actually granted, not from intent: skip
the permission step and the app records the chosen time with the reminder **off**,
rather than claiming a notification it cannot deliver.

A gap the tests caught: the "Başla" button is disabled with an empty selection, so
an error that only appeared on press could never be seen. The requirement is now
stated inline the moment the selection empties.

## 6. Not verified

**The native device matrix is required before release and none of it was run
here.** Everything below is unmeasured:

- **Every notification behaviour on a real device.** No iOS or Android build was
  made. The service is proven against a fake `expo-notifications`, which proves
  the *ordering and reconciliation logic* and nothing about the SDK: that a
  `{type:'daily'}` trigger actually fires daily, that the Android channel makes
  the Android 13 dialog appear, that iOS provisional delivers quietly, that the
  identifier survives a reboot.
- **The specific matrix arch-001 §4 names:** Android 12/13/14 and iOS, reboot,
  timezone and DST change, battery optimisation / Doze, and denied vs provisional
  permission. Also unrun: what the OS does to a daily trigger when the app is
  force-stopped, and store-review behaviour.
- **The deep link.** `deepLinkFor` is unit-tested, but no tap has ever opened the
  app: neither the warm-start listener nor the cold-start
  `getLastNotificationResponseAsync` path has executed.
- **The timezone poll.** The 60 s interval and the offset comparison are not
  exercised by any test, and polling is a weaker mechanism than an OS event —
  a DST shift while the app sits in the foreground is the case to check on device.
- **Onboarding on a device**: keyboard, scroll at 390×844, the real permission
  dialog appearing after the explanatory copy, and how the flow reads in light
  theme. Only the mock-mode render is tested.
- **`app.json`'s plugin** has never been through `expo prebuild`; the icon/colour
  and `defaultChannel` are unvalidated against a real build.
- The permission *hint* copy is shown from state; nobody has seen it next to the
  actual OS settings screen it points at.
