## Verdict

**Request changes: 4 blocking findings, 6 non-blocking findings, and 4
needs-measurement gates.** The live evidence is meaningful: all named functions
are deployed, internal-secret failure is closed, add-source's SSRF/redirect
smokes pass, sync-feeds inserted 334 articles from seven sources with zero

## Blocking findings

### B1 — Daily-cap deferral consumes the jobs' Claude retry budget

**Measured static defect; runtime impact inferred.** Leasing increments
`attempt_count` in SQL (`supabase/migrations/202608210004_jobs_and_rpc.sql:287-322`,
especially `:309-317`). `processEnrichments` leases first and checks the daily
cap afterward (`supabase/functions/_shared/enrichment.ts:313-343`). When the cap
is spent, `requeueForCap` calls the ordinary retry RPC
(`supabase/functions/_shared/enrichment.ts:438-452`), whose SQL clears the lease
but never restores the attempt (`supabase/migrations/202608210007_internal_wrappers_ai.sql:338-375`).
The comment that this is “without consuming an attempt” is therefore false.

Impact (inferred): after the 200-call cap is reached, every worker firing leases
and requeues up to three jobs for the next day while incrementing them. Jobs at
four attempts become queued with `attempt_count=5`; `private.lease_ai_jobs`
requires `< max_attempts`, so they are stranded without Claude ever seeing them.
The Jest fake returns caller-supplied jobs without applying lease semantics
(`supabase/tests/enrichment.test.ts:81-103`), and its cap tests assert only the
retry call (`supabase/tests/enrichment.test.ts:525-559`), so the fake deletes the
load-bearing database behavior from the test.

Smallest safe correction: make “release unattempted lease” an explicit,
lease-token-guarded SQL transition that decrements the just-incremented attempt
(never below zero), and call it only for `daily_cap`; better long-term, define
attempts as actual Claude calls and increment immediately before the call.
Add an integration or stateful fake test that starts at attempt 4, denies the
cap repeatedly, and proves the job remains leaseable at attempt 4.

### B2 — The 8/10-second fetch timeout ends at response headers, not response body

**Measured.** `safeFetch` creates an overall deadline, but clears the abort timer
immediately after `fetchImpl` resolves (`supabase/functions/_shared/url-safety.ts:270-305`).
It then reads the response stream afterward (`supabase/functions/_shared/url-safety.ts:339-340`),
where `reader.read()` has no timer or abort handling
(`supabase/functions/_shared/url-safety.ts:359-395`). A server can return headers
quickly and trickle or stall forever below the 1 MiB cap. Redirect response
bodies are also abandoned without cancellation (`supabase/functions/_shared/url-safety.ts:307-320`).

Impact: the explicit 8-second add-source and 10-second ingestion bounds are not
real end-to-end bounds; a public user-added feed can occupy an Edge invocation,
and one stalled seeded source can hold one ingestion concurrency slot. The only
timeout test stalls before headers (`supabase/tests/url-safety.test.ts:449-466`),
so it cannot detect this path.

Smallest safe correction: keep one abort controller/timer alive through DNS,
all redirects, and full capped-body consumption; translate an abort during
`reader.read()` to `timeout`, cancel every discarded response body, and add a
stream that emits headers then never closes.

### B3 — Feed body text can inject the prompt's closing delimiter

**Measured static defect; model behavior needs measurement.** The prompt says
the article is untrusted only between `ARTICLE_OPEN` and `ARTICLE_CLOSE`
(`supabase/functions/_shared/prompt.ts:60-66`). Titles and source names have both
markers removed (`supabase/functions/_shared/prompt.ts:134-149`), but the body is
trimmed/capped without marker removal (`supabase/functions/_shared/prompt.ts:101-108`)
and interpolated verbatim before the real closing marker
(`supabase/functions/_shared/prompt.ts:127-130`). A user-controlled feed can
include the exact close marker followed by instructions outside the declared
untrusted region.

This does not expose the Anthropic key, but it can corrupt shared cached
summaries/translations while still satisfying the JSON schema. The tests cover
ordinary body instructions and hostile title/source markers, but not a marker
inside `contentText` (`supabase/tests/anthropic.test.ts:185-219`). That misses
the one value rendered inside the fence.

Smallest safe correction: remove or encode both marker strings in the article
body before truncation/interpolation, then assert the constructed block contains
exactly one opening and one closing marker for hostile title, source, and body
fixtures. Bump `PROMPT_VERSION` if the stable prompt text changes; body-only
escaping does not require invalidating prior cache entries.

### B4 — Digest finalization can mark a digest ready with fewer than five items

**Measured static race; runtime interleaving inferred.** Finalize counts eligible
articles in one SQL statement (`supabase/migrations/202608210009_digest_variable_conflict.sql:131-149`),
then deletes/inserts items in later statements (`:151-190`) and unconditionally
marks the digest ready (`:192-202`). Under PostgreSQL's normal READ COMMITTED
behavior, those statements may see different snapshots. If ingestion changes an
article's `content_hash`, or a source changes status, after the count but before
the insert, the insert can select fewer than five and the function still writes
`status='ready'`. The function also reads the digest status without locking its
row (`:118-129`), so simultaneous first finalizers can race into the same
delete/insert and one can fail on the position key.

Impact: the client-visible invariant is “five or none”; RLS exposes a ready
digest, so a four-item ready row is a durable incorrect state. The TypeScript
tests exercise a pure ranker, not the SQL transaction
(`supabase/tests/digest.test.ts:1-8`), and the supplied live smoke had zero
eligible summaries, so this path has not run live.

Smallest safe correction: lock the digest row with `FOR UPDATE`, insert from one
candidate-selection snapshot, capture the actual inserted row count, and mark
ready only when that count is exactly five; otherwise remove partial items and
return `preparing`. Add a database concurrency test for two finalizers and an
article content-hash change at the count/insert seam.

## Non-blocking findings

### N1 — Polling an existing job is charged as a “new miss”

**Measured.** Every cache miss spends the 30/day device budget before the
idempotent enqueue reveals whether the job already existed
(`supabase/functions/_shared/enrichment.ts:200-234`). The contract calls this
budget “30 new misses,” and the response instructs a queued client to poll, so
polls for the same cache key can consume the quota without creating work.

Impact: with the 300-second no-key interval, a user can exhaust a day in 2.5
hours by following the response; at the normal 30-second interval it is 15
minutes. Use an atomic DB wrapper that returns an existing job without charging,
or charges and creates only when the cache-key job is genuinely new. A
read-before-write client fix alone would retain a concurrency race.

### N2 — The JSON “byte cap” reads the full body first and counts UTF-16 units

**Measured.** After an optional `Content-Length` check, `readJsonBody` awaits
`request.text()` before checking size, and compares `text.length` rather than
UTF-8 bytes (`supabase/functions/_shared/auth.ts:82-104`). Chunked requests can
therefore allocate the whole body before rejection, and multibyte input can
exceed the named 16 KiB limit while passing the unit count.

This is bounded in practice only if the Edge gateway has its own request limit,
which is **needs measurement**. Stream/array-buffer the body under a byte cap,
then decode and parse it.

### N3 — `AI_DAILY_CAP=0` is accepted by config but rejected by SQL

**Measured.** Runtime config clamps the cap to `0..100000`
(`supabase/functions/_shared/anthropic-deno.ts:55-77`), while the database rejects
limits below one (`supabase/migrations/202608210004_jobs_and_rpc.sql:342-355`).
Setting zero as an operational kill switch therefore leases jobs and then turns
the cap check into a function error, also interacting badly with B1. Either make
the configuration minimum one or define zero as a pre-lease “disabled” path
that touches no jobs.

### N4 — Ingestion-run close failure is silently swallowed

**Measured.** A failed `finishIngestionRun` call is caught with no warning or
result flag (`supabase/functions/_shared/ingest.ts:128-137`). Articles rightly
remain committed, but the only request log still reports normal completion; the
stale `finished_at IS NULL` row is visible only to someone already querying the
private table. Emit one bounded warning containing run ID and transition code,
without article/feed content.

### N5 — The underlying source-state definer accepts `p_ok = NULL`

**Measured.** `aigundem.internal_update_source_fetch_state` validates source and
next-fetch time but not its boolean (`supabase/migrations/202608210006_internal_wrappers.sql:171-215`).
SQL three-valued logic then takes inconsistent failure branches. The temporary
public transport shim rejects null today, and the typed Edge adapter supplies a
boolean, so this is latent until direct `aigundem` routing or another service
caller is introduced. Add `p_ok is null` to the implementation's argument
validation before the schema is exposed.

### N6 — Migration/deploy reproducibility is outside the committed configuration

**Measured.** Three filenames share version `202608210006`, and two share
`202608210007` (each file header is line 1 under `supabase/migrations/`); the P4
report already records that `apply_migration` by name works but `supabase db
push` collides (`agents/reports/p4.md:263-267`). Also, no committed
`supabase/config.toml` exists at `2b25be8`, while the three cron-only functions
need JWT verification disabled because cron sends only `X-Internal-Secret`.

The current hosted project is applied/deployed and smokes passed, so this is not
a present runtime blocker. Before a second environment or routine redeploy,
document/pin the exact migration ledger and deploy flags, or create a unique
forward migration sequence/config without rewriting already-applied history.

## Test-quality answer: the 42702 class was not caught

**Measured.** The P5 SQL test explicitly says it is static and cannot prove
Postgres accepts the SQL (`supabase/tests/sql-lint-p5.test.ts:1-12`); it reads
only `202608210008_digest_and_cron.sql` (`:24-26`, `:115-119`). No committed test
mentions migration 0009 or `variable_conflict`. The live 42702 was therefore the
first parser/execution evidence, and the forward fix has no regression test.

A focused static lint could flag a PL/pgSQL `RETURNS TABLE` OUT name reused as
an unqualified identifier inside `ON CONFLICT (...)`, or require
`#variable_conflict use_column`/a named constraint for such functions. The
stronger correction is an ephemeral-Postgres migration test that creates the
functions and executes both prepare and finalize; syntax-only parsing would not
exercise this runtime ambiguity. The same database test should preserve lease
attempt semantics for B1 and transaction behavior for B4 instead of replacing
them with fakes.
