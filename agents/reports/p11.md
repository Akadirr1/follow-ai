## §H — Model provider is configuration (for `arch-001.addendum.md`)

**Context.** There is no Anthropic key and there will not be one. The human has
a Google AI Studio key and an NVIDIA NIM key, already in Supabase Vault as
`aigundem_gemini_api_key` and `aigundem_nvidia_api_key`. The enrichment pipeline
does not care which model wrote three Turkish bullets, so the provider became a
configuration choice rather than a rewrite.

**Decision.** One interface, three implementations, one judgement.

1. **The interface does not change.** `ClaudeClient { summarise(input) }` is
   what every provider implements; `SummariseClient`, `SummariseOutcome` and
   `SummariseInput` are neutral aliases added beside it. The Claude-flavoured
   names are kept and re-exported rather than renamed — the existing suites
   import them, and a rename would have been a large diff whose only content was
   churn.
2. **Everything downstream of the HTTP call is shared and unchanged**: the same
   `prompt.ts` article block, the same `parseAndValidate`, the same
   `TokenUsage`, the same `EnrichmentFailureCode` vocabulary, the same retry and
   truncation-escalation rules. A provider cannot be "leniently validated"
   because there is only one validator. A test asserts Gemini and NVIDIA send
   **byte-identical article blocks**.
3. **`resolveAiProvider(env, getSetting, options)`** decides who answers.
   `AI_PROVIDER` ∈ `gemini | nvidia | anthropic | auto` (default `auto` =
   first of gemini → nvidia → anthropic whose key resolves). Keys: environment
   first, Vault second. Anthropic is env-only — its key is not in Vault, and
   adding it to the allow-list would widen a read-any-secret surface for
   nothing.
4. **The model string is part of the summary cache key**, so
   `request-enrichment` and `process-enrichments` must resolve the *same* one.
   Both call the resolver; the agreement is asserted behaviourally and in the
   source.
5. **Fallback**: when the primary returns a *retryable* failure and a second
   provider has a key, the secondary is tried once inside the same job, before
   backoff. A non-retryable failure is never retried elsewhere.
6. **Anthropic stays supported**, unused. `AI_PROVIDER=anthropic` plus a key is
   the rollback path, and none of its code changed.

`Retry-After` is new: it reaches `runOneJob`, which takes `max(backoff, asked)`
capped at an hour. Google's free tier is RPM-limited and says so on a 429;
retrying earlier than it asked just spends the next slot on another 429.

## Three decisions worth your eye

**1. Gemini's schema omits `minItems`/`maxItems`.** You measured that the
OpenAPI subset does not guarantee them. An unsupported key would be a 400 on
*every* call — a fatal risk in exchange for a constraint that buys nothing,
since `parseAndValidate` re-checks the count and the prompt already says "tam
olarak üç". The count is in the schema `description` instead. A test pins the
absence, along with the absence of `additionalProperties` and lowercase types.

**2. An explicit `AI_PROVIDER` is honoured exactly — it does not fall through.**
If you set `nvidia` and only a Gemini key resolves, the answer is "no provider",
not Gemini. Silently answering with a model nobody chose would put that model
string in the cache key. `auto` is how you ask for "whatever works".

**3. The fallback's model does NOT go into the row.** When the secondary
answers, `article_summaries.model` still carries the job's model. This is a
deliberate deviation from the plain reading of "the model column carries the
provider's model string", and the reason is a trap: the row's model is half the
cache key `request-enrichment` looks up. Writing `meta/llama-3.3-70b-instruct`
into a row for a job enqueued as `gemini-2.5-flash` would make that article a
permanent cache miss — the job reads `ready`, so nothing re-enqueues, and the
client polls forever. The producing model is surfaced instead as
`outcomes[].used_model` in the `process_enrichments_done` log, which is where
you would look anyway. Normal (non-fallback) operation is unaffected and *does*
satisfy the brief's intent: rows now say `gemini-2.5-flash` rather than
`claude-opus-5`.

**Related, and worth knowing before you switch providers:** changing
`AI_PROVIDER` orphans jobs already queued under the old model string. They are
processed and written under that old key; `request-enrichment`, now resolving
the new model, misses and enqueues a fresh job. It self-heals at the cost of one
extra call per already-queued article, once, at switch time.

## What is NOT verified

1. **Every live call.** No network, no key. The request shapes match what you
   measured and the response handling matches what you documented, but **no
   request has ever been sent**. The first real call is the first proof.
2. **That Gemini accepts this exact `responseSchema`.** The subset rules came
   from your measurement; my omission of `minItems`/`maxItems` is a judgement
   about a risk I could not test.
3. **That NVIDIA's JSON mode is satisfied by our prompt.** The "JSON" literal is
   pinned, but whether NIM's implementation of the rule matches OpenAI's is
   unverified.
4. **That 0011 parses**, and that `vault.decrypted_secrets` actually holds the
   two entries under those exact names. A name typo degrades to
   `skipped: no_api_key`, which looks like "no key" rather than like an error.
5. **The fallback end to end.** The composite is unit-tested against fake
   clients; a real Gemini 429 handing off to a real NVIDIA call has never
   happened.
6. **Turkish output quality from either model.** No summary has ever been
   generated by anything. Claude's prompt was written for Claude; whether
   `gemini-2.5-flash` and a 70B Llama produce good Turkish under it is unknown
   and is the first thing worth reading by eye.
7. **Cost.** `AI_DAILY_CAP` is a guardrail, not a measurement. Nothing here says
   what a day of Gemini flash actually costs.

## Rollback

Three independent levers, cheapest first:

- **Stop enrichment entirely:** `AI_DAILY_CAP=0` → `skipped: 'disabled'` before
  any lease. Or remove both keys → `skipped: 'no_api_key'`. Both are
  configuration; no redeploy, no migration.
- **Back to Anthropic:** `AI_PROVIDER=anthropic` plus `ANTHROPIC_API_KEY`. None
  of the Anthropic code changed, and its tests are untouched. With no such key
  this resolves to no provider, which is the same safe no-op.
- **Revert 0011:** re-apply 0008's one-name allow-list
  (`'aigundem_automations_secret'`). It is `create or replace` with an identical
  signature, so privileges survive and nothing is dropped. The automations
  secret keeps working; the provider keys stop resolving, which degrades to
  `skipped: no_api_key`.
- **Revert the code:** `git checkout -- supabase scripts` and redeploy both
  functions. Jobs enqueued under a provider model remain in the table under that
  model string; they become orphans exactly as described in decision 3 and
  self-heal on the next request per article.
