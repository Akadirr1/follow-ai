## Parser choice: hand-rolled, and what that costs

`_shared/xml.ts` is a ~325-line tolerant, non-validating XML reader rather than a
pinned dependency. Three reasons, in order of weight:

1. **This task has no network.** No parser could be installed, and — the part
   that matters — no parser could be *executed* here. A dependency that has
   never run once is not the safer choice over code that 28 tests exercise.
2. **Two runtimes.** The functions run on Deno (`npm:`/`jsr:` specifiers), the
   tests on Node. One dependency-free module behaves identically in both, with
   nothing to pin twice and no bundling surprise at deploy.
3. **Real feeds are not valid XML** often enough that strictness is a liability:
   unescaped `&`, a stray `<` in a title, mismatched close tags. A tolerant
   reader degrades to "one bad item" instead of "whole feed rejected".

What it deliberately does **not** do, stated so nobody assumes otherwise:

- **no DTD or entity declarations, and no external entities.** `<!DOCTYPE …>` is
  skipped, never interpreted — XXE is impossible by construction rather than by
  configuration. A fixture carries a `file:///etc/passwd` entity and a test
  asserts it never appears in the parse tree.
- **no namespace resolution.** Prefixes are matched literally
  (`content:encoded`, `dc:creator`), which is what every real feed uses. A feed
  binding `content:` to a different URI would be mis-read.
- **no mixed-content fidelity.** Element text is the concatenation of its direct
  text and CDATA children.
- Entity decoding is **single-pass**, so `&amp;lt;` yields `&lt;`, not `<`.
  Unknown entities are left verbatim rather than dropped.

Boundary neighbours are included on purpose: `172.32.0.1` and `100.128.0.1` sit
one step outside the private and CGNAT ranges and must stay allowed, or a
correct-looking off-by-one would pass unnoticed.

URL-shape rejections, each asserted with its reason: `http:`, `ftp:`, `file:`,
`data:`, `user:pass@`, `user@`, `#fragment`, `:8080`, `:22`, IPv4 literal, IPv6
literal, **public** IPv4 literal, `localhost`, `.local`, `.internal`, `.onion`,
non-absolute, empty, >2048 chars.

Redirects: 3 followed, the 4th refused; a redirect to `http:`, to
`169.254.169.254`, to `.local`, to `:9999`, or to a hostname resolving to
`10.0.0.5` is refused **and the target is never fetched** (asserted on the fetch
log, not just the return value); a redirect without `Location` is refused.

Also enforced and tested: `redirect: 'manual'`, `credentials: 'omit'`, exactly
three headers sent (`accept`, `accept-encoding`, `user-agent`) and no cookie,
conditional headers only when validators exist, declared-oversize rejected
before reading, undeclared oversize rejected mid-stream, abort reported as
`timeout`, transport failure reported as `network_error` with the hostname
scrubbed from the detail.

Two SSRF decisions are stricter than arch-001 and worth your eye:

- **All IP literals are refused, including public ones.** A feed worth adding
  has a name, and allowing literals would remove the DNS classification step.
- **`add-source` fails closed when no DNS resolver exists.** `Deno.resolveDns`
  is not guaranteed on the Supabase Edge runtime. For user input the guard
  returns `dns_unavailable` rather than fetching an unclassified destination.
  `sync-feeds` passes `requireDns: false`, because its hostnames were reviewed
  by a human before seeding and ingestion must not stop dead on a runtime
  detail. **Whether `Deno.resolveDns` exists there is NOT VERIFIED.**

Residual risk, unchanged from arch-001 and not solved: **DNS rebinding.** The
address checked is not provably the address the socket uses. Closing it needs
connect-time destination enforcement, which the Edge runtime does not expose.

## Decisions and deviations

**D1 — `public.aigundem_internal_*` transport shims (your call, addendum §C.1).**
Your commit `e7af55b` recorded that `ALTER ROLE authenticator SET
pgrst.db_schemas` returns 42501. That breaks the Edge Functions the same way it
broke client reads: the exposed-schema list is server config and `service_role`
does not bypass it, so `aigundem.internal_*` was unreachable through
supabase-js. I asked; you chose shims. All eight are `SECURITY DEFINER`,
`set search_path = ''`, fully schema-qualified, **no dynamic SQL**, argument-
validated, `REVOKE ALL … FROM public, anon, authenticated`, `GRANT EXECUTE …
TO service_role` only, and each is a pure delegate to its `aigundem`
implementation — asserted by the lint, which also forbids any table/view/type in
`public` and any `public.` name not matching `aigundem_internal_*`.
They are **not** owned via an explicit `ALTER … OWNER TO postgres`: that is a
no-op when applied as postgres and a hard failure as anyone else, so ownership
follows the applying role exactly as in 0001–0005.

**Reads:** the Edge Functions do not use your `public.aigundem_*_v1` read shims
at all. Every read they need comes back from a wrapper (`lease_due_sources`
returns the source rows). One path, one privilege surface.

**D2 — routing is configuration, not code.** `AIGUNDEM_RPC_SCHEMA` /
`AIGUNDEM_RPC_PREFIX`, defaulting to `public` + `aigundem_` so deploy works
tonight. When the human exposes `aigundem`, set them to `aigundem` + empty. No
redeploy of changed logic.

**D3 — `private.lease_due_sources` widened to `pending`, by compensating
`CREATE OR REPLACE`.** P2's version leases `status = 'active'` only, but
`add-source` creates sources as `pending` *on purpose* — P2's RLS hides
non-active sources, so a source with no articles must stay out of the shared
catalogue. Active-only leasing meant a user-added source would never be fetched
and never become active: **invisible forever.** The signature is identical, so
P2's `aigundem.internal_lease_due_sources` wrapper and every grant from 0005 are
untouched. This is the sanctioned fix for an already-applied migration.

**D4 — one extra wrapper, `internal_lease_source(uuid)`.** arch-001 §3 gives
`sync-feeds` an optional `source_id`, which lease-due cannot express (a named
source is usually not due). It also makes a single-feed remote smoke possible
without waiting 15 minutes. It refuses a `failed` source: reviving one should be
deliberate.

**D5 — migration numbering.** Three files now share prefix `202608210006`
(your `public_read_shims`, my `internal_wrappers`, my `seed_default_sources`)
and `0007` is your catalog shims. You confirmed: apply by name, P5 cron moves to
`0008`. `supabase db push` would collide on version; `apply_migration` will not.
Asserted in the lint so it cannot be forgotten.

**D6 — the `sql` Jest project no longer uses the `jest-expo` preset.** This one
found a real bug in my own tests. Under `jest-expo`, `URL` and `TextDecoder` are
React Native's polyfills: the former does not lowercase hosts, the latter
supports UTF-8 only. Three tests failed for behaviour Deno and Node both have,
and — worse — anything I had *not* tested would have passed under a runtime that
is not the target. `testEnvironment: 'node'` alone is insufficient; the preset's
setup files install the polyfills regardless. The `store` project is unchanged.
This is a slightly wider `jest.config.js` edit than "test location only", and it
is the reason the charset and canonicalisation tests are meaningful.

**D7 — `@supabase/supabase-js` is pinned to `2.45.4`, UNVERIFIED.** No network,
so the registry could not be consulted. I picked a version I am confident
exists over a newer one I would be guessing at. **Confirm or bump before the
first deploy** — it is one line in `supabase/functions/deno.json`.

**D8 — the wrappers migration is 763 lines**, over the 500-line house limit. You
asked for the shims in that specific file; splitting them out would have broken
the instruction and the atomicity of one privilege surface. Flagging, not
arguing.

**D9 — items with an unparseable date are dropped, not defaulted to `now`.**
`published_at` drives feed ordering, so inventing a timestamp parks a mystery
item at the top of every user's feed. Counted in `skipped.no_date` instead.

**D10 — `articles.language` is inherited from the source, not detected.** All
six seeded feeds are single-language, and a wrong guess is worse than no guess:
it would make `process-enrichments` skip an English article's Turkish
translation. Detection belongs to P4, which sees the text anyway.

## What is NOT verified

Everything needing the real database, the real network, or Deno:

1. **That any of this SQL parses.** No parser was installable offline and no
   database was reachable. Syntax is inspection plus a structural scan.
2. **That the wrappers and shims behave** — leasing under `SKIP LOCKED`,
   per-item subtransaction isolation in `internal_upsert_articles`, the
   `pending → active` promotion, the `on conflict … where is_default` inference
   against P2's partial index. All predicted, none executed.
3. **That the seed lands six rows**, and that `extensions`-schema assumptions
   hold.
4. **That the six live feeds parse.** The fixtures are hand-written from
   documented shapes. Real bytes carry namespace, CDATA and entity variation no
   fixture anticipates. **This is the single most likely thing to surprise you.**
5. **Conditional GET.** Facts say deepmind/arxiv/techcrunch send ETags and only
   techcrunch sends Last-Modified. Whether they honour `If-None-Match` with a
   304 is unmeasured; the 304 path is tested only against a fake fetch.
6. **Anything Deno.** `Deno.serve`, `Deno.env`, and especially whether
   `Deno.resolveDns` exists on the Supabase Edge runtime — if it does not,
   `add-source` fails closed on every request until routing or policy changes.
7. **The pinned `@supabase/supabase-js` version** (D7).
8. **`verify_jwt`.** `add-source` assumes the platform default (true) gates it
   with the legacy anon JWT. I set no function config; confirm at deploy.
9. **Real-world charset handling.** `decodeBody` is tested against synthetic
   ISO-8859-9 bytes, not a live Turkish feed.
10. **Rate limiting end to end.** The window arithmetic is tested; that Postgres
    derives the same `window_start` is asserted only by construction
    (epoch-floor on both sides).
