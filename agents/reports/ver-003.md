both web exports, bundle composition, live PostgREST reads, and the live client
repository read path.** The live checks mapped 7 active sources and real articles,
including a non-overlapping keyset continuation and the expected pending-summary

device-only behavior remain unverified, and two acceptance claims are weaker than
their reports imply (the enrichment poll cap has no execution test; persisted
cache restoration has no fetch-order assertion).

Shared-checkout note: the full run measured 803 tests rather than P9's reported
799. The checkout changed concurrently and `main` advanced to fix-003 `2675013`
during verification; later P10 files appeared uncommitted and were ignored. Thus
803 is the exact repository result I observed, not an isolated replay of only the

## 4. Render and route test quality — verified by inspection

### What is realistic

- `src/__tests__/screens.test.tsx` renders the real screen components inside the
  real Theme, TanStack Query, and Toast providers. It replaces repositories at
  the seam, which is the appropriate fake boundary for screen-state tests.
- The screen suite covers visible loading/empty/error/stale/pending/ready states,
  a real debounce, a real second-page button flow, user-state writes, typed
  errors, and route/Linking calls. It does not replace the whole screen with a
  snapshot; there are no snapshots.
- Supabase repository tests fake only the fluent Supabase transport and assert
  table/RPC/filter/order/limit shapes plus row-to-DTO mapping. The separate live
  probe above closes the main risk of a fake fluent builder diverging from
  PostgREST.
- Notification tests use an injected fake OS API and verify the service's state
  machine and API ordering. This is good evidence for pure orchestration logic,
  not for Expo/native delivery.

### Weak or missing negative/integration cases

1. **No test exercises `useEnrichment` through six queued results and proves the
   warning + polling stop.** P6's report points only to the constant/implementation.
2. The query persistence test restores data into a fresh `QueryClient`, but it
   never mounts a query with a fetch spy. “Restore before first fetch” is therefore
   verified by implementation/library usage, not by the named acceptance test.
3. P7's read mutation is split across tests: `openArticle` proves `onOpen` fires
   once, and feed code passes `markRead`, but no render test asserts that “N yeni”
   decrements or that read styling changes after a card opens.
4. P9's schedule test proves schedule precedes cancel and observes the final
   stored ID, but its fake store does not log the storage call, so the precise
   schedule → **persist** → cancel order is verified by source inspection only.
5. `useDigestNotifications` itself has no hook test. Launch/foreground/timezone
   reconciliation and the “permission revoked → update digestEnabled=false”
   integration are only inspected. The service-level `reconcile` matrix is well
   tested.
6. The deep-link pure function is tested, but neither the cold-start
   `getLastNotificationResponseAsync` branch nor the warm listener/subscription
   cleanup is mounted.
7. Settings' notification switch/time-sheet integration is not rendered in the
   P9 suite. Onboarding is rendered, but only with an unsupported notification
   hook fake.

## Single most important gap

**Real-device notification verification is the release-critical gap.** P9's
state machine is thoughtfully tested against fakes, but no evidence shows that
Expo SDK 54 schedules and delivers the daily trigger, survives lifecycle/timezone
conditions, or routes a real tap on supported iOS and Android versions. Within
the automated suite, the sharpest missing case is the `useEnrichment` polling-cap
test; it should be added, but it is lower release risk than an entirely unrun
native notification matrix.
