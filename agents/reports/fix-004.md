## B1 — the daily cap no longer spends a Claude attempt

**Hunks.** New SQL `aigundem.internal_release_ai_job_unattempted` + shim;
`EnrichmentDb.releaseJobUnattempted`; `requeueForCap` calls it instead of
`retryJob`; the false comment is replaced by an explanation of what went wrong.

```sql
aigundem.internal_release_ai_job_unattempted(
  p_job_id uuid, p_lease_token uuid, p_available_at timestamptz,
  p_error_code text default 'daily_cap'
) returns boolean
public.aigundem_internal_release_ai_job_unattempted(<same>) returns boolean
```

It sets `status='queued'`, clears the lease, records `last_error_code`, and
does `attempt_count = greatest(j.attempt_count - 1, 0)` — guarded by
`j.lease_token = p_lease_token and j.status = 'leased'`, so a worker whose lease
expired cannot rewind a job another worker now owns. The floor exists because
P2's `ai_jobs_attempts_non_negative` would reject a negative row.

It is called from the cap path and nowhere else. Every other path keeps the
increment, because it really did spend an attempt.

### The stateful fake

The old fake returned whatever job the caller handed it and applied no database
rules — which is precisely why nothing caught this. The new `statefulDb`
implements the three transitions the bug lived between:

```
lease   : status in (queued,leased) AND available_at <= now
          AND attempt_count < max_attempts
          -> attempt_count += 1, status = leased, fresh token
release : token matches AND status = leased -> attempt_count -= 1 (floor 0)
retry   : token matches                      -> attempt UNCHANGED
```

The retry/release asymmetry is the point: a fake that cannot tell them apart
cannot see the defect.

The headline test starts a job at attempt 4 of 5, denies the cap three times,
and asserts `attempt_count === 4` and `status === 'queued'` after each — then
leases again and gets it. The clock advances 36 h between runs, because a
deferral parks the job at the next daily window; without that, runs two and
three would find nothing due and prove nothing.

**I verified the test actually catches the bug**: reverting `requeueForCap` to
`retryJob` fails 5 tests; restoring the fix passes all 54. Two tests also guard
the opposite error — a job whose Claude call genuinely failed still spends its
attempt, and six real failures still exhaust the budget and land `failed`. B1
must not make jobs immortal, only stop the cap from charging them.

fix-003's `no_content` terminal failure is untouched and still tested.

## B2 — the fetch deadline now covers the body

**Hunks.** `safeFetch` creates **one** `AbortController` and **one** timer before
the redirect loop and clears it in a `finally`; the per-hop controller is gone;
`readCapped` takes the signal; every discarded body is cancelled.

The body read races each `reader.read()` against the abort signal rather than
trusting the runtime to tear the stream down. Both halves matter: a real `fetch`
does reject a pending read on abort, but the case that hung — a peer holding the
connection open below the 1 MiB cap — is exactly where that is least certain,
and a hand-built stream in a test is not wired to the signal at all. The race
**resolves** with a sentinel rather than rejecting, so a read that wins cannot
leave an unhandled rejection behind, and one listener covers the whole read
rather than one per chunk.

Five new tests: headers-then-stall times out inside the budget and the stream is
cancelled; a redirect chain is bounded by one deadline (the old per-hop timer
would have allowed 4×); a redirect body is cancelled; a non-2xx body is
cancelled; and — the guard against overcorrecting — a slow-but-finishing body
still succeeds.

## B3 — the article body can no longer close the fence

**Hunks.** `stripMarkers()` extracted and exported; `sanitiseLine` now delegates
to it; `buildArticleBlock` applies it to `contentText` **before** truncation.

Before was `article.contentText.trim()`: the body was the one value rendered
*inside* the fence and the only one whose markers were never removed. Stripping
before the cut also stops a truncation landing mid-marker and keeps `charsSent`
honest.

Removal, not escaping — the markers are arbitrary tokens no real article
contains, so deleting them loses nothing, whereas an escaped marker would still
depend on the model respecting the escape.

Six new tests assert **exactly one** opening and one closing marker for a
hostile body, a hostile title, a hostile source, and all three at once; that an
innocent body is byte-identical; and that `PROMPT_VERSION` stays `v1`, because
the stable system text did not change and invalidating every cached summary
would be pure cost.

## B4 — digest finalize is five-or-none

**Hunks.** `aigundem.internal_digest_prepare/finalize` re-created in 0010,
keeping `#variable_conflict use_column` from 0009.

```sql
aigundem.internal_digest_prepare(p_date date default null)
  returns table (digest_date date, status text, item_count integer, missing integer)
aigundem.internal_digest_finalize(p_date date default null)  -- same signature
```

Finalize now:

1. `select … from aigundem.digests d where d.digest_date = v_date **for update**`
   — serialises finalizers for the date, so the second waits and then sees the
   first's committed `ready` and no-ops instead of racing into the same
   delete/insert;
2. has **no pre-count at all** — the seam is removed, not narrowed. The single
   `INSERT … SELECT` is the one and only observation of the candidate set;
3. `get diagnostics v_inserted = row_count`;
4. `if v_inserted = 5 then` … `set status = 'ready'` — the only place `ready` is
   written. Otherwise it deletes the partial rows and returns `preparing` with
   `missing = 5 - v_inserted`, which is the number the client needs rather than
   an estimate from a different snapshot.

`prepare` is now explicitly advisory: it writes no items and decides nothing;
its count is a readiness report. The ranking clauses are unchanged — B4 changes
the transaction shape, not the ranker — and the lint pins them.

`sql-lint-0010.test.ts` pins `for update` before the insert, the absence of
`v_candidates`, `get diagnostics`, the `= 5` guard, exactly one `set status =
'ready'`, both deletes, `search_path = ''`, the pragma, and every revoke/grant.

## N1 — polling no longer charges the miss budget

```sql
aigundem.internal_enqueue_ai_job_charged(
  p_article_id uuid, p_content_hash text, p_prompt_version text, p_model text,
  p_subject text, p_action text, p_window_start timestamptz, p_limit integer
) returns table (job_id uuid, status text, created boolean,
                 charged boolean, allowed boolean)
public.aigundem_internal_enqueue_ai_job_charged(<same>)
```

One function body, therefore one transaction, in the order you confirmed:

1. `INSERT … ON CONFLICT DO NOTHING RETURNING id` — the insert, not a prior
   `SELECT`, decides "genuinely new", and decides it atomically;
2. nothing inserted → return the existing job with `charged=false`;
3. inserted → charge; if the charge denies, **delete the row just inserted** and
   return `allowed=false`. The row was invisible to every other transaction
   until commit, so removing it leaves no window in which an over-budget request
   created work.

`requestEnrichment` replaces bump-then-enqueue with this single call. Tests
cover both branches on the action list: an existing job produces one
`bumpRateLimit` (the hourly check) and no daily charge; a new job charges once.

## N3 — `AI_DAILY_CAP=0` is a kill switch

`processEnrichments` returns `{skipped:'disabled', ready:0, retried:0, failed:0}`
**before leasing** when the cap is ≤ 0. The config layer accepted 0 while
`private.bump_rate_limit` rejects any limit below 1, so the old order leased
jobs — incrementing their attempts, interacting with B1 — and then turned the
cap check into a function error. `ProcessResult.skipped` gains `'disabled'`,
distinct from `'daily_cap'` (budget spent) and `'no_api_key'`.

Three tests, using the stateful fake so "touches no jobs" is a real assertion
about `attempt_count` and `status`, not just about call counts.

## N4 — a swallowed run-close failure now says so

or upstream error string, and the serialised line is under 200 characters; and a

## N5 — the source-state definer rejects a null boolean

`aigundem.internal_update_source_fetch_state` re-created verbatim from 0006 plus
`if p_ok is null then raise`. With a NULL boolean every `case when p_ok` silently

unchanged — a behaviour change smuggled into a null-check fix would be worse
than the fix is worth.

## What stays NOT verified without Postgres

1. **That any of 0010 parses.** No parser offline, no database reachable. The
   lint is structural. 0009 exists because exactly this class of error (42702)
   reached the live project — the pragma is pinned now, but pinning is not
   parsing.
2. **B4's concurrency claim.** That `for update` actually serialises two
   finalizers, and that `get diagnostics` reports what the insert wrote, are
   both unexercised. The TypeScript tests cover the pure ranker, not the
   transaction. **This is the highest-value thing your smoke can check**: two
   concurrent finalize calls, and a content-hash change between count and
   insert.
3. **B1's SQL half.** The stateful fake asserts the *semantics* I wrote into
   `internal_release_ai_job_unattempted`; that the SQL implements those
   semantics is unproven. A live check is cheap: lease a job, note
   `attempt_count`, call the release with the right token, confirm it went back
   by one and that a wrong token returns false and changes nothing.
4. **N1's atomicity.** The insert-then-charge-then-delete sequence relies on the
   function body being one transaction. True for a PostgREST RPC, unverified
   here.
5. **N5**, which is entirely SQL and has no runtime test at all.
6. **B2 against a real network peer.** The tests use hand-built streams; a real
   TLS peer that stalls mid-body is the case that matters and cannot be
   reproduced offline.
7. **Whether the Hugging Face / enrichment path ever produces five eligible
   summaries.** With no Anthropic key nothing is enriched, so the digest still
   correctly stays `preparing` and B4's `ready` branch cannot be smoked without
   hand-inserted summary rows.

  `internal_digest_prepare`/`finalize` from **0009** (not 0008 — 0009 carries

  redeploy. That reinstates all four blockers, so prefer reverting one finding
