## 0. The blocker, first

**B1 — every Edge write from the app is rejected. `add-source` and every summary
request fail in supabase mode.**

`src/data-access/supabase/edge.ts:153`

```ts
export const clientRequestId = (): string =>
  `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
```

Both functions validate that field:

```ts
// supabase/functions/add-source/index.ts:114, request-enrichment/index.ts:61
if (!isUuidV4(fields.client_request_id)) {
  throw new AppError('bad_request', 'client_request_id must be a uuid v4.');
}
```

`isUuidV4` is `/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i`.
The client sends e.g. `mt2ag1uw-uwh0plq2`. Result: **400 bad_request** on every
add-source and every request-enrichment call, surfaced to the user as
"Geçerli bir adres gir (https:// ile başlamalı)." for a perfectly good feed URL,
and as a summary that never leaves "Özet hazırlanıyor".

Why nothing caught it: the client suite asserts `typeof client_request_id ===
'string'`; the server suite constructs its own uuids. Each lane tested its own
assumption. This test crosses the boundary, which is the entire point of P10.

`src/identity/deviceId.ts` already contains a correct uuid v4 generator, and
`edge.ts` already imports from that module — so the fix is one line plus an
export rename:

```ts
// src/identity/deviceId.ts — rename the existing generator, keep a thin alias
export function randomUuidV4(): string { /* current generateDeviceId body */ }
export const generateDeviceId = randomUuidV4;

// src/data-access/supabase/edge.ts
import { getDeviceId, randomUuidV4 } from '../../identity/deviceId';
export const clientRequestId = (): string => randomUuidV4();
```

`edge.ts` is **not** in P10's allowed paths, so I did not apply it. The defect is
pinned by a test that will fail the moment the fix lands, and the failing line
names this report:

```
src/__tests__/integration.test.tsx
  › BLOCKING B1: client_request_id is not the uuid v4 the server demands
```

Whoever fixes it flips two assertions in that test. Recommend dispatching it as
fix-006 (client lane, ~5 minutes including the test flip).

Every other suite in this repo fakes at the repository boundary. These fake one
level lower: a **real `@supabase/supabase-js` client** over a stub `fetch`, so a
request travels screen → hook → repository → query builder → HTTP, and the
assertions read the URL that was actually produced. A wrong view name, a dropped
filter or a broken keyset passes every other test in the repo and fails here.

## 3. Release scripts

### `scripts/check-env.mjs`

Parses `src/config/env.ts` for `process.env.EXPO_PUBLIC_*` reads and
`scripts/env.example` for assignments, and fails on: a mismatch either way, any
`EXPO_PUBLIC_`-prefixed secret name (`ANTHROPIC_API_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `AUTOMATIONS_SECRET`, `SERVICE_ROLE`), or a
`process.env` read anywhere in `app/` or `src/` outside the one sanctioned file.
Text parsing, not import: importing the module would read the ambient
environment instead of the declarations.

### `scripts/check-bundle.mjs`

`npx expo export --platform web --clear`, then scans `dist/`.

Two design decisions worth stating:

**It is precise, not merely strict.** A bare substring scan reports `sb_secret`
as a leak, because supabase-js ships `e.startsWith("sb_secret_")` — a
format check, not a value. So each forbidden token carries a credential-shaped
regex and an allowlist entry with a `why` and a proof `context`; anything that is
neither credential-shaped nor allowlisted fails as **unknown**, so a new
occurrence gets investigated rather than absorbed.

**It decodes JWTs.** A substring scan cannot tell an anon key from a service-role
key — both are `eyJ…`. Every JWT-shaped string in the bundle is decoded and its
`role` claim reported; `service_role` or `supabase_admin` fails the build. Today:
`embedded JWT role(s): anon`.

**`--clear` is load-bearing.** Measured during this task: a cached Metro build
gave `url: 0 | key: 0 | view: 1` — the view name present, the credentials
missing, because the transform was cached from before the values were set. A
production build in that state falls back to mock and ships the prototype data
while every other check stays green. The script now forces a clean export *and*
asserts the URL and key are present in supabase mode, so it cannot pass silently
again. `p10-smoke.md` §5.2 repeats the warning for `expo start`.

### `npm run check:release`

```
npm run typecheck && npm test && node scripts/check-env.mjs
  && node scripts/check-bundle.mjs && node scripts/check-bundle.mjs --mode=mock
```

The mock pass is the mirror image: it asserts the project URL and the anon key
are **absent**. That is what catches a release accidentally built from a dev
profile, and vice versa.

**Changed from the brief's draft:** `npm test -- --runInBand` is now plain
`npm test`. In band, the run finishes and then hangs — "Jest did not exit one
second after the test run has completed" — intermittently, on the full two-project
run. It is a leaked handle in the RN environment that `--detectOpenHandles` does
not surface; in worker mode Jest force-exits the straggler and the run takes 5.7 s
instead of 11 s. A release gate that can hang forever is worse than one that
force-exits a worker. Flagged as N3.

## 4. Production data mode

`EXPO_PUBLIC_DATA_MODE` unset now resolves by build type: `supabase` for a
release bundle, `mock` for dev and test, keyed on `__DEV__` (Metro defines it in
every bundle; Jest sets it too, so no test needed configuring). An explicit value
always wins in both directions.

The subtle part is that **`FALLBACK_DATA_MODE` had to be split from
`DEFAULT_DATA_MODE`**. Both fallback branches — invalid mode string, and
`supabase` with a missing URL or key — return `mock` explicitly. Had they kept
returning "the default", a production build with a missing key would have
"fallen back" to supabase and looped. Four tests pin this.

## 7. Findings besides B1

**N1 — Turkish copy drift between the lanes.** The client's `CODE_MAP` in
`edge.ts` keys on `invalid_url`, `blocked_host`, `not_a_feed`, `duplicate_source`,
`too_many_requests`. The server's `ErrorCode` union has none of those; it emits
`unsafe_url`, `parse_failed`, `rate_limited`, `bad_request`. Most fall through to
a sane `invalid_input`, but `parse_failed` — "this URL is not a feed" — reaches
the user as "Geçerli bir adres gir (https:// ile başlamalı)", which is the wrong
advice for a valid https URL. One-line fix in the same place as B1: map
`parse_failed → unsupported_source`, `unsafe_url → invalid_input`,
`rate_limited → rate_limited`. Pinned by a test that names this finding.
Also: `duplicate_source` is unreachable — an existing feed returns **200**, not
409, so "Bu kaynak zaten ekli." can never be shown.

**N2 — two nested retry layers on the read path.** postgrest-js retries 503 and
520 itself, three times, with 1 s/2 s/4 s backoff. React Query then retries the
whole thing twice more. A PostgREST cold start therefore takes up to ~21 s before
the user sees the offline banner, with a spinner throughout. Not changed here (no
feature changes in P10); worth a decision later — either disable one layer or
show the stale-cache banner while the retries run.

**N3 — `jest --runInBand` can hang after the run completes.** See §3. Worked
around by dropping the flag; the leaked handle is still there and
`--detectOpenHandles` does not find it.
