transport shim — and nothing else. No `create or replace`, no drop, no table:

## The SQL

```sql
aigundem.internal_enqueue_digest_candidates(
  p_date           date,
  p_model          text,
  p_prompt_version text,
  p_per_source     integer default 2,
  p_limit          integer default 15
) returns table (enqueued integer, already integer, candidates integer)
```

plus `public.aigundem_internal_enqueue_digest_candidates(date, text, text,
integer, integer)` with the same shape (addendum §C.1). SECURITY DEFINER,
`search_path = ''`, schema-qualified throughout, no dynamic SQL, arguments
validated, revoked from public/anon/authenticated, granted to `service_role`
alone, `#variable_conflict use_column`.

Candidate set: articles from `active` sources, in the window, with a non-empty
`content_text` (fix-003 — a body-less Hugging Face item would buy a guaranteed
`no_content` refusal), and **no `article_summaries` row matching all four of
`(article_id, content_hash, p_prompt_version, p_model)`**. Ranked
`row_number() over (partition by source_id order by published_at desc, id desc)`,
kept at `<= p_per_source`, then `order by published_at desc, id desc limit
p_limit`. Inserted into `private.ai_jobs` with `on conflict (article_id,
content_hash, prompt_version, model) do nothing` — 0004's `ai_jobs_cache_key`,
the same one `request-enrichment` relies on.

Two properties are worth naming because they are the ones that cost money if
they are wrong:

**One statement.** The selection, the per-source ranking, the cap and the insert
are a single data-modifying CTE. `candidates` and `enqueued` are counted from
the same snapshot, so `already = candidates − enqueued` is arithmetic on one
world, not two. A count-then-insert pair under READ COMMITTED would not be.

**No rate-limit charge.** `internal_enqueue_ai_job_charged` (0010) exists
because a *device* spending the system's money needs a budget. Here the system
spends its own on its own schedule; there is no subject to charge, and any
subject invented for the purpose would silently shrink some real device's
30/day. The lint test pins the absence of `bump_rate_limit`, `p_subject` and
`rate_limit_buckets`.

## The daily spend bound

```
per prepare run  =  min( DIGEST_PER_SOURCE × active sources , DIGEST_CANDIDATES )
                 =  min( 2 × 6 , 15 )  =  12 jobs/day
```

`already` grows and `enqueued` shrinks as the day's articles get summarised, so
12 is the ceiling on a cold day, not the steady state. Above it sit two more
bounds that do not move: the worker's global `AI_DAILY_CAP` (200), and the
worker's own throughput — `ai-gundem-ai-worker` runs `*/2` with `max_jobs: 3`
(the 0008 job body), so the 02:45→03:30 UTC gap is ~22 firings × 3 = **66 job
slots for at most 15 jobs**. Draining is not the constraint.

Adding a seventh source raises the first number by 2 and nothing else changes
until 8 sources, where `DIGEST_CANDIDATES` starts to bind. That is what the
overall cap is for.

## Environment

| Name | Default | Range | Notes |
|---|---|---|---|
| `DIGEST_PER_SOURCE` | `2` | 1–5 | server-side only, no `EXPO_PUBLIC_` |
| `DIGEST_CANDIDATES` | `15` | 1–50 | server-side only, no `EXPO_PUBLIC_` |

Neither needs to be set. Both are **clamped, not validated**: 0012 *raises* on
an out-of-range argument, so passing a typo'd `DIGEST_CANDIDATES=5000` straight
through would make the whole prepare phase throw and the day's digest row would
never be created. A deploy variable must not be able to take a daily job down.
The SQL guard remains the real boundary; the clamp only guarantees we never hand
it something it refuses. **`0` is not an off switch — it clamps to 1.** See
Rollback for what actually disables this.

## Three decisions worth your eye

**1. The model comes from the resolver, not from a default.** Prepare calls
P11's `resolveAiProvider` over the same env-then-Vault path the worker uses. This
is the whole reason the change is not three lines: the model string is half the
summary cache key, so enqueueing under a plausible-but-wrong model produces jobs
the worker happily executes, summaries written under a key nothing looks up
again, and no error anywhere. Tests assert the resolver's model is what reaches
the wrapper, for all three providers, and that `index.ts` contains no
hard-coded model literal.

**2. Pre-enrichment fails soft — this deviates from the brief, which specified
only `no_provider`.** A `DigestDbError` from the wrapper is caught and reported
as `reason: 'enqueue_failed'` with `enqueued: 0`, rather than propagated. The
reason is deploy ordering: if `build-digest` ships before 0012 is applied, the
RPC 404s, and without this the prepare cron would 500 and **stop creating the
day's digest row at all** — a regression caused entirely by an improvement.
Pre-enrichment is an optimisation; the digest row is not. Non-`DigestDbError`
throws still propagate, so a real bug is not swallowed.

**3. Prepare enqueues; it does not wait.** Nothing blocks on the jobs draining.
The 02:45 prepare and the 03:30/40/50 finalizes are already the retry loop, and
66 worker slots sit between them.

## What is NOT verified

1. **That the SQL parses, plans and runs.** No database. The CTE reads correctly
   and the pieces mirror 0010's, but `internal_enqueue_digest_candidates` has
   never executed.
2. **That the counts are right.** `already = candidates − enqueued` depends on
   `picked` being materialised (it is referenced twice, which normally forces
   it) rather than re-planned per reference. Unproven without a database, and it
   is the assumption I would test first.
3. **That the anti-join actually excludes today's already-summarised articles.**
   The four columns are pinned by a lint test; whether they match real rows is
   an assertion about data I cannot see.
4. **The end-to-end chain** prepare → 12 jobs → worker → 12 summaries →
   finalize → `ready`. Every link has been exercised alone; the chain never has.
5. **That 12 candidates yields 5 digest items.** Finalize needs five articles
   from the window with summaries, ranked round-robin by source. If several
   enrichments fail (a refusal, a truncation, a body that turns out to be
   boilerplate) the digest stays `preparing` and the honest fix is a higher
   `DIGEST_PER_SOURCE`, not a change here.
6. **Cost.** 12 Gemini flash calls a day is a count, not a price. Nothing here
   measures what it costs.
7. **The `npm test` exit.** It exited cleanly on this run; I did not verify why,
   and the fix-004 finding should not be considered closed on this evidence.

## Rollback

0012 is additive, so "revert the migration" is rarely the right lever. In
increasing order of blast radius:

- **Stop pre-enrichment only:** redeploy the previous `build-digest`. The
  function is the only caller; the SQL then simply sits unused. Nothing else in
  the system references it.
- **Cheaper, no redeploy:** there is no env value that disables it —
  `DIGEST_CANDIDATES=0` clamps to 1, which still enqueues one job a day. The
  nearest configuration-only lever is `DIGEST_PER_SOURCE=1` +
  `DIGEST_CANDIDATES=1`, i.e. one article a day, not zero. **If you want a real
  off switch, say so and I will add `DIGEST_PRE_ENRICH=off` — it is a
  ten-line change.** I did not invent a third knob unasked.
- **Stop all enrichment spend:** `AI_DAILY_CAP=0`. The worker then skips every
  job, digest-enqueued or user-requested. Jobs accumulate as `queued` and drain
  when the cap returns.
- **Disable the cron:** `cron.unschedule('ai-gundem-digest-prepare')`. Finalize
  keeps working; it creates its own digest row.
- **Undo the queued work:** the jobs are ordinary `private.ai_jobs` rows with
  `status = 'queued'`. Deleting the ones this created is safe — nothing
  references them until they are leased — but a summary already written is a
  cache hit for a real user and is worth keeping.
- **Drop the functions** (last resort, only if 0012 itself is the problem):
  `drop function public.aigundem_internal_enqueue_digest_candidates(date, text,
  text, integer, integer);` then the `aigundem.` one. Redeploy the old
  `build-digest` first, or prepare will report `enqueue_failed` every night —
  ineffective, but noisy.
