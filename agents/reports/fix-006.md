# fix-006 — onboarding completion now reaches the root guard

The transition is state-driven: nothing navigates, the guard flips, and React
Navigation swaps the stack itself. Confirmed against a real navigator in Jest,
including a negative probe that reproduces the original symptom exactly.

---

## 1. Root cause — confirmed, with lines

Three facts that were each fine alone:

1. **`app/_layout.tsx`, old `useOnboardingState`** — `useState(undefined)` plus a
   mount `useEffect` calling `getOnboardingCompletedAt()` **once**, with a
   `cancelled` flag and an empty dependency array. One read per mount, ever.
2. **`src/user-state/onboarding.ts:154`** (`completeOnboarding`) — writes
   `P9_KEYS.onboardingCompletedAt` to KV and returns. Nothing told the layout,
   because there was nothing to tell.
3. **`app/onboarding.tsx:94`** — `router.replace('/(tabs)')` immediately after.

So after the tap: the marker is on disk, `onboarding.completed` is still `false`,
`<Stack.Protected guard={onboarding.completed}>` (`app/_layout.tsx:167`) still
has `(tabs)` unmounted, and the replace addresses a route that **is not in the
navigator**:

```
The action 'REPLACE' with payload {"name":"(tabs)",…} was not handled by any
navigator. Do you have a route named '(tabs)'?
```

React Navigation's unhandled-action path is a no-op, so the user stays on
onboarding until a cold restart, when the first KV read finally returns the
marker. The device symptom and the `imperative-api.js` stack frame match this
exactly.

`ver-004` §4 had named the blind spot: no test mounted the real
`Stack.Protected`. Every onboarding test mocked `useRouter`, so
`expect(mockReplace).toHaveBeenCalledWith('/(tabs)')` **passed on the broken
build** — the assertion could not distinguish "navigated" from "navigated
nowhere".

## 2. Hunks

| File | Change |
|---|---|
| `src/user-state/onboarding.ts:33–101` | new external store: `OnboardingSnapshot`, `getOnboardingSnapshot()`, `subscribeOnboarding()`, `primeOnboardingState()`, `publishOnboarding()` (private), `resetOnboardingStateForTests()` |
| `src/user-state/onboarding.ts:157` | `completeOnboarding` publishes **after** the marker write |
| `src/user-state/onboarding.ts:162–165` | `resetOnboarding` became `async` and publishes `null` |
| `app/_layout.tsx:75–89` | `useOnboardingState` → `useSyncExternalStore` + prime on mount |
| `app/onboarding.tsx:91–98` | `router.replace('/(tabs)')` removed, with the reason in place of the call; `useRouter` import and `const router` dropped |
| tests | 2 new files (15 tests), 1 updated |

The async getters (`getOnboardingCompletedAt`, `isOnboardingComplete`) are
untouched and still exported — existing suites use them.

Three details that are load-bearing rather than decoration:

- **Publish after the write, never before.** A publish that outran a failed
  `setItem` would put the user in the tabs with no marker to survive the next
  launch — the exact inverse of this bug and harder to notice.
- **`undefined` survives into the snapshot.** The launch gate needs "not read
  yet" to be distinct from "not completed", or the first frame flashes onboarding
  at a returning user.
- **`getServerSnapshot` is passed** (the third argument). Static rendering for
  the web export calls it, and `useSyncExternalStore` throws during SSR without
  one. Server-side it answers `undefined`, the gate stays closed and the layout
  renders `null` — precisely what the effect-based version did on the server.
  This is why A3 still passes.

## 3. Which redirect mechanism, and how it was verified

**No redirect call at all.** The chain, read in `expo-router@6.0.24` and
`@react-navigation/routers`:

1. `node_modules/expo-router/build/layouts/withLayoutContext.js:81-83` —
   `useFilterScreenChildren` walks the children; `const excludeChildren =
   exclude || !child.props.guard`, and a `<Protected guard={false}>`'s children
   are added to `protectedScreens`.
2. `node_modules/expo-router/build/useScreens.js:123` — `useSortedScreens` does
   `.filter((item) => !protectedScreens.has(item.route.route))`. A guarded-off
   screen is not rendered as a `Screen` at all, so it leaves the navigator's
   `routeNames`. (`Protected` itself is just `Group`:
   `build/views/Protected.js`.)
3. `node_modules/@react-navigation/routers/src/StackRouter.tsx:266-303` —
   `getStateForRouteNamesChange` filters `state.routes` down to names still in
   `routeNames`; **if none remain it pushes `routeNames[0]`** (there is no
   `initialRouteName` on the root layout, so the fallback is index 0).

At the moment of the flip the only route on the stack is `onboarding`, which has
just left `routeNames` — so the filtered array is empty and the router pushes the
first now-visible screen. `useSortedScreens` keeps user-declared order
(`build/useScreens.js:61-70`, file-system routes appended after), and
`app/_layout.tsx` declares `(tabs)` first inside the completed guard, so
`routeNames[0]` is `(tabs)`.

**Verified empirically, not only by reading.**
`src/__tests__/onboarding-routing.test.tsx` mounts the real `app/_layout.tsx`
under `renderRouter` and asserts `getPathname()` goes `/onboarding` → `/` on
completion, with `console.error`/`warn` watched for `was not handled by any
navigator` and `Do you have a route named`.

**Negative probe.** I temporarily removed the single `publishOnboarding(completedAt)`
line and re-ran that test:

```
× swaps to the tabs when completion publishes, with no unhandled action
  Expected: "/"
  Received: "/onboarding"
```

That is the reported bug, reproduced in Jest. The line was restored immediately;
the suite is green as shipped. So the test fails for the right reason, which is
the only evidence that matters for a regression this quiet.

`renderRouter` runs fine in this Jest setup — no fallback was needed.

## 4. Test boundaries: what each one fakes

**15 new tests** (store project 345 → 360). Nothing else in the repo changed
behaviour.

### `src/__tests__/onboarding-routing.test.tsx` (3) — fakes *nothing* about routing

The real `app/_layout.tsx`, the real `<Stack>`, the real `<Stack.Protected>`, the
real `useOnboardingState`, a real `completeOnboarding()`. Only the leaf screens
are stubs (`ONBOARDING` / `FEED` / …), because what is under test is *which one
the navigator mounts*. Fonts, splash and the notification deep link are mocked —
they gate rendering and are not part of the question.

- incomplete device → only `onboarding` is mounted, `FEED` is unreachable,
  pathname `/onboarding`;
- press → pathname `/`, `FEED` on screen, `ONBOARDING` gone, and **no** unhandled-action
  message on either console channel;
- a cold start with the marker already on disk (snapshot dropped, re-read from
  storage) lands on `/` directly.

This is the test class ver-004 §4 said was missing, and the one that would have
caught the bug.

### `src/user-state/__tests__/onboarding-store.test.ts` (12) — fakes *storage* only

A `Map` with a read counter. Store and hook are both real, so "the second
subscriber flipped" is a statement about the notification, not about a mock.

- Store (8): unread → `null` / stored instant; **one** storage read for N primes;
  a throwing read publishes `null` rather than hanging the splash; subscribers
  fire on completion and on reset and stop after unsubscribe; an unchanged value
  does **not** notify; a refused completion (`no_sources`) does not publish.
- Hook (4): `isReady:false` on the first frame (`undefined`, not `false`); then
  `completed:false`; then `true` **on the same mounted instance** after
  `completeOnboarding()`; a second mounted subscriber flips with it; a reset
  takes it back to `false`.

### `src/__tests__/onboarding-screen.test.tsx` (updated)

The assertion that hid the bug is inverted: the screen must now **not** navigate.
It asserts the marker is persisted, `mockReplace` was **not** called, and the
published snapshot equals the stored instant.

## 7. Rollback

- **Smallest:** put `router.replace('/(tabs)')` back in `app/onboarding.tsx`
  **inside an effect keyed on `completed === true`** — never in the `start`
  handler, which is what raced the guard. The store must stay for that to work.
- **Full:** revert `app/_layout.tsx` to the `useState` + mount-effect read and
  drop lines 33–101 of `src/user-state/onboarding.ts`, plus the publish in
  `completeOnboarding` and the `async` on `resetOnboarding`. That restores the
  bug, so it is only a step on the way somewhere else.
- The store is additive: every existing async getter kept its signature, so
  nothing outside these three files depends on the new exports.
