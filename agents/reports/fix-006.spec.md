# fix-006 — Onboarding completion never reaches the root guard → "REPLACE (tabs) was not handled" (implementer, client lane)

**Role:** implementer. Read `agents/implementer.md`. Worker rules: no spawning, no
graph queries, no `.orchestrator/`, no task-status updates; never `git add`/
`commit`/`stash`/`checkout`. No other worker is active.

## Measured on a real iOS device (human, 2026-08-21)
After tapping the onboarding "start" button the app logs
`The action 'REPLACE' with payload {"name":"(tabs)",…} was not handled by any
navigator. Do you have a route named '(tabs)'?` and stays on onboarding. The
stack shows `router.replace` fired from a passive effect (`imperative-api.js`).

## Root cause (coordinator, by inspection — confirm and cite lines)
- `app/_layout.tsx` `useOnboardingState()` reads `getOnboardingCompletedAt()`
  **once** in a mount effect and never re-reads. `completeOnboarding()`
  (`src/user-state/onboarding.ts`) only writes KV; nothing tells the layout.
- So `onboarding.completed` stays `false`, `<Stack.Protected guard={completed}>`
  never mounts `(tabs)`, and `app/onboarding.tsx:94` `router.replace('/(tabs)')`
  targets a route that does not exist in the navigator → unhandled. The user is
  stuck until a cold restart (when the first KV read finally returns the marker).
- ver-004 §4 had flagged exactly this blind spot: "real `Stack.Protected`
  routing not mounted" in any test.

## Change
1. **Make completion reactive.** In `src/user-state/onboarding.ts` add a tiny
   external store: `subscribeOnboarding(listener)`, `getOnboardingSnapshot()`
   (`undefined` = not read yet, `null` = incomplete, ISO string = complete),
   `primeOnboardingState()` (one async KV read, memoised) and have
   `completeOnboarding()` (and any reset helper) update the snapshot **after**
   the marker write succeeds and notify subscribers. Keep the existing async
   getters working (tests use them).
2. **`app/_layout.tsx` `useOnboardingState`** → `useSyncExternalStore`
   (+ prime on mount). Semantics unchanged: `isReady` false until the first read
   resolves; `completed` flips the moment `completeOnboarding()` finishes.
3. **`app/onboarding.tsx`:** remove the `router.replace('/(tabs)')` — Expo
   Router 6 `Stack.Protected` redirects automatically when the current screen's
   guard turns false and `(tabs)` becomes available (verify against
   `node_modules/expo-router/build/**` — if you find the auto-redirect does
   **not** happen in 6.0.24, keep a `router.replace('/(tabs)')` but run it in
   an effect keyed on `completed === true`, i.e. only after the guard flipped).
   Either way the transition must be driven by state, never by a route that
   may not be mounted.
4. **Tests:**
   a. `useOnboardingState` hook: starts `isReady:false`; after the primed read
      → `completed:false`; after `completeOnboarding()` → `completed:true`
      **without remount**; a second mounted subscriber sees the same flip.
   b. Route-level: render the real root `Stack` (or a minimal
      `Stack`+`Stack.Protected` mirror of `_layout.tsx` with the real
      `useOnboardingState`) under `expo-router` testing utils
      (`renderRouter` from `expo-router/testing-library`) with an incomplete
      device → only `onboarding` is reachable; complete onboarding → the
      current pathname becomes `/` (tabs) with no "not handled" warning
      (spy on `console.error`/`warn`). If `renderRouter` cannot run in this
      Jest setup, say exactly why and keep (a) plus a unit test proving
      `onboarding.tsx` no longer navigates into a guarded route.
   c. Existing suites unchanged.
